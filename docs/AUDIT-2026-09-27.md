# Auditoría técnica — 2026-09-27

## Alcance

Auditoría del estado real del repositorio `Proyecto_App_Androd`, contrastando la implementación de `main` con el contexto/prompt maestro del proyecto ERP.

## Hallazgos principales

### CRÍTICO — aislamiento multitenant

El middleware anterior aceptaba `x-tenant-id` cuando no existía un tenant previamente establecido en la request. Esto permitía que el cliente propusiera el contexto tenant. La corrección aplicada hace que el `tenantId` del JWT sea la fuente autoritativa y que un header diferente produzca HTTP 403. Las requests protegidas sin tenant autenticado producen HTTP 401.

### ALTO — inventario materializado ausente

El diseño documentado exige mantener `stock_balances` y actualizarlo dentro de la misma transacción que la venta. El repositorio auditado solo calculaba stock mediante agregación histórica. Se agregó `StockBalanceModel` y actualización atómica para salidas.

### ALTO — venta confiaba demasiado en datos enviados por el cliente

La creación de factura aceptaba descripción, SKU, precio y datos financieros desde el payload. Se corrigió el flujo para resolver el producto por `tenantId + sku`, verificar que `productId` corresponda al producto encontrado y derivar descripción/precio desde catálogo. El stock se valida de forma atómica.

### ALTO — número de factura

Se agregó índice único compuesto `{ tenantId, number }` para impedir folios duplicados dentro de un tenant.

### MEDIO — auditoría forense incompleta

El middleware de auditoría registra `req.body` como `changes`, pero esto representa el payload recibido y no un diff `before/after`. El modelo deberá evolucionar para cumplir el requisito forense completo.

### MEDIO — autenticación incompleta

Existe middleware JWT/RBAC, pero el repositorio auditado no demuestra un módulo completo de registro/login/gestión de usuarios montado en la API. Esto queda como trabajo pendiente.

### MEDIO — catálogos incompletos

Existen modelos para productos y contactos, pero no se encontró evidencia de CRUD completo expuesto por API en el estado auditado.

### MEDIO — frontend/native no demostrados

El contexto del proyecto exige React Native/Web y Kotlin para hardware. El estado auditado del repositorio no demuestra esas piezas completas.

## Estado de verificación

Los cambios fueron aplicados en la rama `audit/fix-core-security-and-integrity` para revisión antes de fusionar a `main`.

No se afirma que `typecheck`, Vitest, integración MongoDB Atlas o E2E hayan sido ejecutados desde este entorno. Deben ejecutarse en un workspace local/CI con las variables de entorno y MongoDB disponibles.

## Regla para la siguiente fase

No agregar nuevos módulos ERP de gran alcance hasta cerrar autenticación/tenant isolation, catálogos, stock materializado, pruebas de transacción y validación del backend.
